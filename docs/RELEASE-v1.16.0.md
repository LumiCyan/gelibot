# GeLi Bot v1.16.0

把 QQ 群接到 Minecraft 服务器的 Windows 桌面端。这一版带来**双服务器验证流程**——
玩家在 QQ 里发一条指令，验证码直接飞进他在验证服的对话框，验完自动进正服白名单。

## 本版核心：双服务器绑定流程

### 解决的是什么问题

服务器开了正版白名单，想让玩家先过一道验证再放进来。老做法有两个毛病：

- 「双向验证模式」要求**玩家先在服务器里取码**——可这需要服务端插件桥，
  而插件桥一直没做（见旧版「已知限制」），等于这条路走不通；
- 「信任模式」直接绑，等于谁报个 ID 就归谁，冒用成本为零。

**新流程全程只用 RCON，不需要任何服务端插件**，方向反过来：验证码由 QQ 侧发起、
投递到游戏内。

### 完整流程

```
① 玩家用待绑定的 ID 登录【验证服】
       ↓
② 玩家在 QQ 群内发送   /绑定 Steve
       ↓
   机器人回复「请查看验证码」
   程序签发一次性验证码，经【验证服】RCON
   把验证码 tellraw 到 Steve 的游戏内对话框
       ↓
③ 玩家在 QQ 群内发送   /绑定 482913
       ↓
   校验通过 → 建立绑定
   → 经【主服】RCON 执行 whitelist add Steve
```

### 两个 RCON 完全独立

| 通道 | 负责 |
| ---- | ---- |
| **主服 RCON** | 日常指令（`/在线`、`/tps` 等）、白名单管理、加白 |
| **验证服 RCON** | 只负责把验证码投进玩家对话框 |

可以在同一台机器上用不同端口（默认 `25575` / `25576`），也可以是两台机器。
两者各自独立配置、独立测试、独立重连，顶栏各占一个状态灯。

### 那些「看起来能跑但其实是坑」的地方

这一版在这些细节上花了最多功夫：

- **玩家不在线时，`tellraw` 也算「执行成功」**。
  RCON 会正常返回，只是响应文本里带一句 `No player was found`。
  所以程序必须**检查响应内容**才能判断验证码到底送到没有——否则就是「提示他去看验证码，
  但游戏里什么都没有」。现在识别到未在线会直接作废该码并提示玩家先登录验证服。

- **验证码绑定到发起者 QQ**。
  验证码是显示在游戏里的，同服其他人可能看到。所以签发时记下发起者，
  别人拿这张码来用会被拒绝，而且**不会**把发起者的码误消费掉。

- **输错验证码 vs 想换绑另一个 ID**。
  两者在群里长得一样（都是一串字符）。判定顺序是：
  命中码池 → 完成绑定；没命中但手上还有未使用的码、且这个串「长得像验证码」（位数与字符集都对）
  → 判为输错，明确提示；否则当作玩家 ID 发起新绑定。
  换绑另一个 ID 时，旧码会一并作废——同一 QQ 同一时刻只保留一张有效码。

- **发码前先预检**。
  数量上限、ID 合法性、是否已被他人占用、自助绑定开关，全部在**发码之前**跑一遍。
  否则会出现「码发过去了、玩家也填了、最后一步告诉他已经被人绑了」的糟糕体验。

- **加白失败不会吞掉绑定**。
  绑定成功但加白失败时，回复里会明确警示并给出可用的补救指令
  （`/加白 <玩家ID>`），不会让你以为一切正常。

### 可配置项

| 配置项 | 说明 |
| ---- | ---- |
| 启用开关 | 关掉后行为与旧版本完全一致 |
| 验证服 RCON | 地址 / 端口 / 密码 / 超时 / 重连间隔 |
| 自动加白 | 可关闭，改由管理员人工审核 |
| 加白命令模板 | 默认 `whitelist add {player}`，`{player}` 会被替换成已验证的玩家 ID |
| 验证码位数 | 4–12 位（沿用原有配置） |
| 验证码字符集 / 有效期 | 纯数字 / 纯字母 / 混合；默认 300 秒 |

## 这一版包含的功能

- **双服务器验证流程**（本版新增，见上）
- **内置 SnowLuma**：一键启动器，自动开后台、直取登录凭据、数据目录分离、随程序退出
- **账号绑定双模式**：双向验证（游戏内取码 + 群内提交）／社交平台信任（群里直接绑）
- **验证码**：位数、字符集（易混淆字符已剔除）、有效期可配，一次性语义，重取作废旧码
- **强制绑定**：未绑定进服踢出（RCON kick）
- **退群自动解绑**、**绑定后改群名片**（三种策略）
- **可自定义消息模板**（7 个文案，支持 `#code` `#time` `#player` `#qq` `#why` 占位符）
- **权限路由**：群 / 私聊 / 管理员三类白名单，9 条内置指令
- **安全**：指令走模板 + 参数白名单校验（`^[A-Za-z0-9_]{3,16}$`），杜绝拼接注入；同用户限流
- **全量审计日志**：每条指令执行与拦截都有记录（含验证服发码与主服加白）
- **6 个功能页面**的图形界面

## 快速开始

1. 双击 `GeLi Bot v1.16.0.exe`（首次启动需 3–10 秒解包）
2. 「连接设置」页 → 点 **启动 SnowLuma** → 自动打开后台 `http://127.0.0.1:5099`
3. 后台里扫码登录 QQ
4. 后台 → **节点配置 → WS 服务端**，复制 **accessToken**
5. 回到本程序，填入 `ws://127.0.0.1:3001` 和刚复制的 Token，**保存配置**
6. 顶栏「QQ」变绿即通

### 想用双服务器流程

1. 验证服与主服的 `server.properties` 都开 RCON（`enable-rcon=true`，各自设强密码）
2. 「连接设置 → Minecraft 服务器（RCON）」填**主服**
3. 「连接设置 → 验证服」勾选启用，填**验证服**的地址 / 端口 / 密码
4. 两个「测试连接」都点一下，确认能执行 `list`
5. 「账号绑定」页确认模式为「双向验证」，按需调整验证码位数与有效期
6. 让玩家先登录验证服，然后在群里发 `/绑定 <玩家ID>`

> **最容易踩的坑**：Token 必须与服务端完全一致。服务端设了 Token 而这边留空，握手会直接 401。
> 界面上的固定提示与错误横幅都会提醒这一点。

## 已知限制

- **服务端插件桥仍未实现**：玩家在游戏内打 `/easybot bind` 无法直接触发取码。
  不过本版的双服务器流程已经绕开了这个需求——它在 QQ 侧发起、把码投进游戏内，全程只用 RCON。
  插件桥现在只对「想在游戏里直接取码」这一种场景还有价值。

- **RCON 密码明文存储**在 `config.json`，请确保该目录权限可控。
  RCON 走明文 TCP，务必只在 `127.0.0.1` 监听，不要暴露到公网。

- **仅 portable 单文件版**，暂无安装版（无开始菜单快捷方式与卸载项）。
