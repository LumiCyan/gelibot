# 2026-10-15 工作日志

## 技术咨询：用现有 OneBot v11 协议接入微信的可行性

用户提问「使用当前协议接入微信的可能性」。做了代码耦合度分析 + 微信侧现状调研，
结论是**协议层可复用，但平台能力与合规性才是真正的瓶颈**。

### 代码耦合度（结论：改造量小）

- `src/main/onebot.ts` 已经是薄适配层，对外只暴露 `sendGroupMessage` /
  `sendPrivateMessage` / `setGroupCard` / `call`，事件只 emit `message` / `event` / `state`。
- **领域层的 ID 已经是 `string`**：`types.ts` 里 `Binding.qq`、`binding.groupId`、
  `audit.userId` 都是 string，不需要改。
- **`set_group_card` 已经走注入**：`router.setGroupCardProvider()`，
  且 `router.ts` 里有 `if (!this.setGroupCardImpl) return;` —— 微信没有群名片能力也不会崩，
  不注入 provider 即可优雅降级。
- **唯一的硬破坏点**：`onebot.ts` 里把 ID 做 `Number()` 强转（OneBot v11 要求 QQ 号是 int）。
  微信 wxid 是字符串（如 `wxid_abc123`），`Number("wxid_abc")` → `NaN`。
  共 4 处：`sendGroupMessage` / `sendPrivateMessage` / `setGroupCard` 的参数转换。

### 微信侧三条路径（调研结论）

| 方案 | 群消息 | 私聊 | 合规 | 备注 |
| ---- | ------ | ---- | ---- | ---- |
| 企业微信 · 群机器人 Webhook | 不能 | 不能 | 合法 | 只能推送，20 条/分钟 |
| 企业微信 · 自建应用 | 不能 | 能 | 合法 | **拉不进群**，只能 1:1 会话 |
| 企业微信 · 会话内容存档 | 只能读 | 只能读 | 合法 | 需企业认证+权限申请，属审计用途 |
| 微信公众号 | 无群聊 | 能 | 合法 | 被动回复 5 秒超时 |
| 个人微信 · Hook | 能 | 能 | 违反 ToS | 封号风险 |

关键事实来源：企业微信开发者社区官方答复
（`developer.work.weixin.qq.com` 问题 16544162326855624137）明确
「机器人功能只支持主动推送消息，不支持被动回复」，且「自建的应用又没法拉到企业微信群里」。

**核心矛盾**：真正被需求的是「玩家微信群里的机器人」，而唯一能合法读群消息的
会话内容存档是审计功能（需企业认证+单独申请），拿它当 bot 属滥用；
能力完全对得上的个人微信 Hook 恰好违规。

### WeChatFerry 现状（重要）

- **仓库已于 2025-05-27 归档，转为只读，官方停止维护**。
- 依赖特定微信客户端版本（3.9.5.26 / 3.9.12.17），微信一升级就失效。
- Windows-only，DLL 注入。
- 违反微信服务条款，封号风险真实存在。
- 生态：Python `wcferry`、Node `@wechatferry/core`、`@wechatferry/puppet`；
  OneBot 侧只有 `nonebot-adapter-wcf`（Python 插件，作者自述「佛系更新」），
  **没有成熟且活跃维护的独立 OneBot v11 微信 WS 服务端**。

### 给用户的建议（架构方向）

**不要内置微信支持**，而是把 QQ 特有的假设摘掉，只承诺「连一个 OneBot v11 端点」：

1. `onebot.ts` 的 `Number()` 改成「能安全转数字就转，否则原样传字符串」。
2. `get_login_info` 失败时降级（不阻塞连接）。
3. 界面与错误文案从「QQ」泛化为「消息平台」，「SnowLuma」泛化为「OneBot 实现」。
4. 群名片不注入 provider 即可降级（已支持）。

好处：仓库内不含任何逆向代码，合规风险留在使用者侧，且顺带支持其他 OneBot 实现。

### 未决

用户尚未表态是否推进，也未决定走哪条路。若推进，优先级建议：
先做协议泛化（低风险、纯增量），再考虑是否在文档里指引用户自行接第三方微信桥。

## 追加 3：服务端插件桥（/easybot bind）的通讯方案梳理

用户提问：实现 EasyBot 式服务器插件时，**插件怎么与"非本地部署"的软件端通讯**；只列方案。
已核对：EasyBot 模型 = 插件作客户端主动连主程序（默认 `localhost:5001` + token），
非本地 = 改 `host` 指向主程序机器地址。

关键约束（决定可行域）：面板服一般只映射游戏端口、不许插件监听新端口，但 JVM 出站自由；
家用软件端入站被 NAT 挡（多无公网 v4）、出站自由且可常驻隧道/订阅器。

已列四族 + 15 项（供后续选型，**尚未选择**）：
- A 直连：①插件出站→软件端监听（端口映射+DDNS/公网 IPv6）②软件端出站→插件开额外端口
  （面板服不行）③端口复用（独服代理分流，折腾级）
- B 中间人：④反向隧道 frp/ngrok/Cloudflare Tunnel/SSH -R ⑤中转节点（VPS/CF Workers+DO/托管 MQTT）
  ⑥现成实时消息服务（ntfy/PubNub/Ably，订阅方出站）⑦虚拟组网 Tailscale/ZeroTier/WireGuard
  （面板服装不了）⑧WebRTC 打洞（理论项，Java 缺轮子）
- C 借道已有通道：⑨**RCON 轮询/长轮询**（零新设施，任何开 RCON 的远程服可用，bind 场景 2–5s 够用）
  ⑩**假人玩家通道**（mineflayer 等登服，走游戏端口天然穿透，代价：占玩家位/正版账号/反作弊）
  ⑪宿主面板 API/SFTP（绑宿主、要凭据）
- D 换位/换信使：⑫客户端 mod 当信使（仅装 mod 玩家在线时通，匹配 bind 场景）
  ⑬**零实时通道**（共享密钥 + 带时效签名码，两侧离线验证，只需抄一次配置）
  ⑭软件端就近部署（同机/同内网退回 localhost）

可行性速记：家用 PC + 面板服 → 不加设施的可行集 = 轮询 / 假人 / 签名码；要实时再加 中转/隧道/推送服务。

## 追加 4：宝塔面板能否当中转节点（继续只做判断，不动手）

用户提问「宝塔面板可以搭建中转吗还是只说可能性」。已查证并给结论：**可以**。

**消歧（关键）**：宝塔面板 = 自己租的 VPS 上的服务器管理面板 → 能当中转宿主；
MC 面板服的控制面板（MCSManager/翼龙）→ 不行（无 root、不许装服务、只映射游戏端口）。
两者常被混为一谈，答复里已点明。

**宝塔上四种可用载体**（均已查证存在）：
- 软件商店「Frp 管理器」插件 → 图形化 frps（bind_port 7000 + token），最省事
- Docker 应用商店的 FRPS 镜像 → 一键装、带 dashboard（默认 7500），内存约 9 MB
- Node/Python 项目管理器或 Docker 自建 WS/MQTT 中继
- Nginx 反代 + Let's Encrypt → 给上面任意一个套 wss:// 外壳

**三个已确认的坑**：
1. 宝塔 Nginx 反代**默认丢弃 Upgrade/Connection 头**，必须手加
   `proxy_http_version 1.1` + `Upgrade $http_upgrade` + `Connection "upgrade"`；
   且要改站点配置而非全局 nginx.conf（升级会覆盖）。
2. `proxy_read_timeout` 默认 **60 秒**，空闲 WebSocket 必被掐断（code 1006），
   需调大 + 应用层心跳。
3. 安全面：宝塔有历史漏洞记录，8888 面板端口不能裸奔；中转服务要 token 认证，
   frp 可用 `allow_ports` 限端口白名单。另：国内 VPS 上中转走非 80/443 高位端口
   不涉及备案。

**结论口径**：宝塔降的是人力成本，不改物理约束（仍需一台公网可达机器、两端仍需出站、
延迟仍多一跳）。已有常开宝塔 VPS → 边际成本≈0，划算；专门买 VPS 则不如直接跑
frps + systemd（少一个面板攻击面）；不想运维则用 Cloudflare Tunnel 跳过整条路。

## 追加 5：中转选型落定（用户给出实际条件）

用户条件：电脑端约束不计；**已有一台买了的宝塔 VPS，上面部署了服务器官网**；
MC 服务器本身是买的面板插件服。问「该用哪个」。

**结论：用宝塔 VPS 做唯一中转入口，选 frp + 复用官网 443（≈方案⑤的增强版，不新开端口）。**

角色锁定：电脑 = 被访问方（跑 GeLi Bot 本体）；宝塔 VPS = 唯一「公网可达 + 完全控制 +
已有域名证书」的机器 → 当入口；面板插件服 = 只能出站 → 只能当客户端。

数据路径：插件出站 → `wss://官网域名/bridge/` → Nginx(443，复用现有证书) →
反向代理到 `127.0.0.1:15001` → frp 隧道 → 电脑 frpc → GeLi Bot 监听端口。
frpc 主动连 VPS 的 frp 控制端口（默认 7000）。

否决项：方案① 直连（要动路由器端口映射/DDNS）；方案⑥ 自建中继（要写代码，frp 已覆盖）；
方案⑪ 假人通道（占玩家位/需正版账号/反作弊）。方案⑩ RCON 轮询此时仍可行，
但有现成 VPS 就浪费了，实时双向更值。

必处理细节：① Nginx 手加 WS 三件套（宝塔默认丢 Upgrade 头）② proxy_read_timeout 调大 +
应用层心跳 ③ 15001 不开进云安全组（只给本机 Nginx 用），对外只需 443 + frp 控制端口，
宝塔自己的 8888 限来源 IP。

**架构建议（趁插件桥尚未实现先定）**：插件侧目标地址做成配置项，桌面端监听地址不写死
127.0.0.1 —— 本地部署 = `http://127.0.0.1:5001`，非本地 = `wss://官网域名/bridge/`，
同一套代码改配置即可。

## 追加 6：v1.16.0 双服务器验证流程实施（RCON-only，无服务端插件）

用户需求：验证服 + 真服分开；玩家登验证服 → QQ 发 `绑定 <ID>` → 机器人回「请查看验证码」
→ 经 RCON 把**可自定义位数**的验证码送到玩家游戏内对话框 → 玩家在 QQ 回填 →
经 RCON 把玩家加进真服（原版白名单）；**两套 RCON 配置完全分开**；其余不变；发新版本。

**最终架构（双 RconClient）**
- `rcon`（主服）：日常指令 + 白名单添加，端口默认 25575。
- `rconVerify`（验证服）：只负责送码，端口默认 25576。
- 两套配置、两条连接状态、两个测试/重连入口；UI 是独立「验证服」卡片 + 顶部独立状态点。
- `verifyServer.enabled` 默认 **false** → 老用户行为 100% 不变，旧配置自动补全该块。

**四个坑（实现时踩出来，已写进代码与测试）**
1. **`tellraw` 对离线玩家仍返回成功**：RCON 的 `success` 只代表指令被服务端接收，
   目标不在线时错误信息只在 **response 文本**里。→ 新增 `PLAYER_NOT_FOUND_RE`
   （英文 + 中文服务端两种措辞），命中即判未送达并 `codes.cancel(rec.code)` 撤销验证码，
   避免池里留一条永远送不到的记录。
2. **验证码归属**：`BindCodeRecord.qq` 记录发码的 QQ，他人拿到码也不能用。
   归属校验必须放在 **delete 之前**（`consume()` 内），否则截码者一用就把原主的码烧掉。
3. **`/绑定 <参数>` 二义性**：code 模式下参数既可能是验证码也可能是玩家 ID。三级判定：
   ① 码在池里 → 直接完成绑定；② 未命中但调用者有 pending 码且参数 `looksLikeCode()`
   → 报「验证码不正确」；③ 其余一律当玩家 ID，走验证服发码。
   `looksLikeCode()` = 长度等于 `codeLength` 且每字符都在 `CODE_CHARSETS[codeFormat]` 里。
4. **「码收到了但绑不上」**：新增 `precheckQqBind()`，把 `commit()` 用的那道闸门
   （`checkCommit`）在**发码前**先跑一遍（自助绑定开关、ID 合法性、数量上限、已被占用）。
   发码后才发现不能绑 = 最差体验。

**其他细节**
- 一个 QQ 同时只保留一个 pending 码（`cancelPendingOfQq`），换绑会作废旧码。
- 加白失败**不吞掉绑定结果**：绑定照样成立，只追加一行
  `[白名单] ⚠ 加入白名单失败：…（可让管理员手动 /加白 xxx）`。
- `whitelistAddCommand` 模板（`whitelist add {player}`）便于换成权限插件指令。
- `Store.loadConfig` 必须**嵌套合并**：`verifyServer.rcon` 是两层，要像 `binding`
  一样显式展开，否则老配置里缺的 rcon 子字段会变成 undefined。

**测试**：新增 `scripts/tests/test-verify-flow.cjs`（**72 项**），内置**两个互相独立的
假 RCON**（`mainCalls` / `verifyCalls`）与 `mainState` / `verifyState` 注入故障。
覆盖：默认值与老配置升级 / 发码 / 玩家不在线 / 归属校验 / 输错 vs 换绑 / 预检 /
未启用验证服时保持旧行为 / 加白开关模板与失败提示 / 帮助文案。
**总数 245 → 317 项**（76 绑定 + 40 路由 + 72 双服 + 39 迁移 + 64 SnowLuma + 26 连接错误）。

**产物**：`dist-release-v1160b/GeLi Bot v1.16.0.exe`，**97,697,975 字节**，
SHA256 `efbc1ac55…adaaadc5`；内嵌图标 7 档与 `build/icon.ico` 逐字节一致。

**踩坑（构建顺序）**：第一次打包 `dist-release-v1160` 时我在后台构建**进行中**
改了 `src/main/binding.ts`（补 `enforceLimit`），产物里是旧逻辑。
→ 教训：**改源码必须在打包开始前全部结束**；交付前用
`grep -c "checkCommit(qq, name, { enforceLimit })" dist/main/binding.js` 反查产物与源码一致。
